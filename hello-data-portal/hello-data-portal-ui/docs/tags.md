# HelloData Portal — Tag & Label System

## Overview

The portal uses **two distinct visual concepts** that are often called "tags" colloquially but serve
different purposes and must never be mixed:

| Concept | Component | Use case |
|---|---|---|
| **User tag** | `<app-tag-chip>` | Free-text labels applied by users to dashboard comments |
| **System label badge** | `<p-tag>` (PrimeNG) | Status indicators, role names, metadata |

---

## User Tags — `<app-tag-chip>`

User tags are strings entered by end-users when creating or editing dashboard comments.
They are stored as comma-separated text on the comment version entity, normalized to
**lowercase** and **at most 10 characters** on write (enforced by `DashboardCommentService`).

### Component location

```
src/app/shared/components/tag-chip/tag-chip.component.ts
```

### API

```html
<!-- Display-only chip (teal pill) -->
<app-tag-chip [tag]="tag" />

<!-- Editable chip with remove button (gray pill) -->
<app-tag-chip [tag]="tag" [removable]="true" (removed)="removeTag(tag)" />

<!-- Compact size for tight layouts (e.g. inline compose area) -->
<app-tag-chip [tag]="tag" [removable]="true" size="sm" (removed)="removeTag(tag)" />
```

| Input | Type | Default | Description |
|---|---|---|---|
| `tag` | `string` | *(required)* | The tag text to display |
| `removable` | `boolean` | `false` | Shows a × remove button when true |
| `size` | `'sm' \| 'md'` | `'md'` | Compact (`sm`) or normal (`md`) size |

| Output | Payload | Description |
|---|---|---|
| `removed` | `void` | Emitted when the user activates the remove button |

### Visual variants

| Variant | Trigger | Appearance |
|---|---|---|
| Display | `removable=false` | Teal pill — signals "this tag is applied" |
| Editable | `removable=true` | Gray pill — signals "this chip can be removed" |
| Compact | `size="sm"` | Reduced font-size and padding for dense layouts |

### Do not redefine styles locally

All styles live in `tag-chip.component.scss`.
Do **not** re-declare `.tag-chip`, `.tag-item`, or `.tag-remove` in individual component SCSS files.

## System Label Badges — `<p-tag>`

System labels are generated by the application to communicate status, roles, permissions,
query durations, and other metadata to the user. Use PrimeNG `<p-tag>` with an appropriate
`severity` value. **Never** use `<app-tag-chip>` for system-generated content.

### Severity mapping

#### Comment status

| Status | Severity | Color |
|---|---|---|
| `PUBLISHED` | `success` | Green |
| `DRAFT` | `warn` | Amber |
| `READY_FOR_REVIEW` | `info` | Teal |
| `DECLINED` | `danger` | Red |
| `DELETED` | `secondary` | Gray |

The mapping is centralized in `DashboardCommentUtilsService.getStatusSeverity()`.
Both `domain-comments` and `comments-feed` delegate to this method — do not inline the
switch logic in templates or other components.

#### Roles and permissions

Use `severity="info"` for business-domain roles and `severity="secondary"` for data-domain
and subsystem roles. This gives roles a neutral, non-alarming appearance.

#### General rules

- Use `severity` whenever the badge communicates a state with semantic meaning (success/warning/error).
- Omit `severity` (defaults to PrimeNG's neutral style) only for purely informational labels
  with no status meaning.
- Do **not** add `icon="fa-solid fa-tag"` to `<p-tag>` — the tag icon implies user-generated
  content and creates confusion with `<app-tag-chip>`.

### Global severity color overrides

The severity palette is aligned with the HelloData teal brand in `src/styles.scss`:

```scss
.p-tag-success { background: rgba(14,124,124,0.12); color: #0e7c7c; }
.p-tag-info    { background: rgba(14,124,124,0.12); color: #0e7c7c; }
.p-tag-warn    { background: rgba(161,98,7,0.12);   color: #a16207; }
.p-tag-danger  { background: rgba(217,54,54,0.12);  color: #d93636; }
```

## Centralized Tag Management

Not implemented. At the time of writing, user tags exist only in the dashboard-comment domain
and are auto-completed from a per-dashboard tag list
(`GET /dashboards/{contextKey}/{dashboardId}/comments/tags`).

A global tag registry (`TagEntity`, `TagRepository`, `GET /tags`, management UI) should be
introduced only when user tags are adopted by additional entities such as datasets, pipelines,
or dashboards themselves.
